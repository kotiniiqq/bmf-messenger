# BMF Messenger — техническое задание на реализацию

Документ описывает, что строим, из чего, в каком порядке и по каким критериям считаем этап готовым.
Все решения ниже — принятые, а не варианты на обсуждение. Отклонение от них фиксируется в `docs/decisions/`.

---

## 1. Что это

Десктопный мессенджер со встроенной почтой, музыкальным плеером, заметками и ИИ-помощником.
Ключевое отличие от конкурентов — **глубокая кастомизация** (темы и оформление как конфиг, маркет) и
**контроль пользователя над своими данными** (свой ключ ИИ, свой почтовый ящик, режим приватности).

Платформы первого релиза: **Windows и Linux**. Мобильные — позже, но протокол проектируется с их учётом.

Домен: `bmf.ink`. Почтовые адреса вида `user@bmf.ink`.
Отдельный домен под почту в старой зоне (`.com`) будет добавлен позже как альтернатива — код должен
поддерживать **несколько почтовых доменов** с самого начала.

---

## 2. Стек

**Сервер:** Node.js 22 LTS + TypeScript, Fastify, WebSocket (`ws`, без Socket.io).
**База:** PostgreSQL 16. Redis 7 — сессии, присутствие, очереди, pub/sub между процессами.
**Файлы:** MinIO (S3-совместимое), локально на VPS.
**Звонки:** LiveKit (SFU) + coturn (TURN/STUN), оба self-hosted.
**Почта:** Stalwart Mail Server (SMTP/IMAP/JMAP).
**Клиент:** Electron 32+ · React 18 · TypeScript · Zustand · Vite. Сборка — electron-builder.
**Наблюдаемость:** Sentry (ошибки), Prometheus + Grafana (метрики), Uptime Kuma (доступность).
**CI/CD:** GitHub Actions.

Язык кода, комментариев, коммитов, имён веток и документации — **английский**.
Пользовательский интерфейс — русский, но через i18n-словари (структура на будущее).

## 3. Репозитории

| Репозиторий | Видимость | Содержимое |
|---|---|---|
| `bmf-messenger/bmf-app` | private | монорепо: `server/`, `desktop/`, `shared/` |
| `bmf-messenger/bmf-releases` | **public** | только собранные бинарники + `latest.yml` / `latest-linux.yml` |

## 4. Архитектурные решения (принятые)

**Аутентификация — только токены.** Access (15 мин) + refresh (30 дней). Никаких серверных
куки-сессий: мобильные клиенты появятся позже, и переделывать нельзя. Каждое устройство —
отдельная запись сессии со своим refresh-токеном, отзывается независимо.

**REST для запрос-ответ, WebSocket только для событий.** Клиент после переподключения обязан
уметь догнать пропущенное через REST (`GET /sync?since=cursor`), а не полагаться на сокет.
Это требование мобильных клиентов, которые не держат соединение постоянно.

**Курсорная пагинация везде.** Никаких `OFFSET` в списках сообщений и писем.

**Идемпотентность отправки.** Клиент генерирует `client_msg_id` (UUID); сервер при повторе
возвращает уже созданное сообщение. Без этого при обрывах связи будут дубли.

**Шифрование.** По умолчанию: TLS в транспорте + шифрование при хранении. История синхронизируется,
поиск работает. Дополнительно — **режим приватности**: кнопка в чате «Предложить режим приватности»,
собеседник подтверждает, дальше E2E через **libsignal** (готовая библиотека, своя криптография
запрещена). В E2E-чатах история не синхронизируется между устройствами и не восстанавливается —
это явно написано в интерфейсе. Пункта в общих настройках нет, решение принимается в контексте чата.

**Права и роли.** Роли участников: `owner`, `admin`, `member`. Права проверяются **на сервере**,
клиентские проверки — только для скрытия кнопок. То же касается премиума: флаг живёт в базе,
клиент ему не хозяин.

**Мультиустройственность.** Прочитанное, черновики, настройки и статус синхронизируются между
устройствами через события. Конфликты решаются по правилу «последняя запись побеждает» с
серверными временными метками.

**Оптимизация заложена сразу, но без преждевременности.** Индексы, курсоры, лимиты, батчинг
событий — да. Шардирование, кластеры, Kafka — нет.

## 6. Протокол

### REST (префикс `/api/v1`)

```
POST   /auth/register            username, email, password → tokens
POST   /auth/login               → tokens + device
POST   /auth/refresh             → new access
POST   /auth/logout              отзыв текущего устройства
GET    /auth/devices             список сессий
DELETE /auth/devices/:id         отозвать чужую сессию

GET    /sync?since=<cursor>      всё пропущенное: сообщения, прочитанное, статусы
GET    /chats                    список с последним сообщением и счётчиками
POST   /chats                    создать группу/канал (title, members[], roles)
DELETE /chats/:id                удалить у себя: выход из группы, очистка личной переписки
                                 (docs/decisions/0006-deleting-a-chat-is-per-member.md)
GET    /chats/:id/members        участники с профилями и ролями
GET    /chats/:id/messages?before=<cursor>&limit=50
POST   /chats/:id/messages       client_msg_id обязателен
PATCH  /messages/:id             правка
DELETE /messages/:id
POST   /messages/:id/reactions   emoji
POST   /chats/:id/pin            message_id + pinned | null — снять все
POST   /media/upload             multipart → bucket_key + превью
GET    /search?q=&scope=&from=&has=&before=    сквозной поиск (чаты, почта, заметки)

GET    /contacts                 свои контакты с локальными именами
PUT    /contacts/:userId         добавить или переименовать (local_name)
DELETE /contacts/:userId         убрать из контактов

GET    /mail/accounts            свои и подключённые ящики
POST   /mail/accounts            подключить IMAP/SMTP
GET    /mail/:account/:folder?before=
POST   /mail/:account/send
POST   /mail/:account/rules      конструктор правил
POST   /mail/:id/unsubscribe

POST   /calls/:chatId/start      → LiveKit token + room
POST   /calls/:id/end
GET    /me, PATCH /me            профиль, статус, настройки
GET    /me/export                архив своих данных
DELETE /me                       полное удаление аккаунта каскадом
```

### WebSocket

Одно соединение на устройство, авторизация access-токеном при handshake.
События — плоские объекты `{ type, payload, ts, cursor }`.

```
server → client:  message.new, message.edit, message.delete, message.reaction,
                  chat.update, chat.member, read.update, presence.update,
                  typing.start, call.incoming, call.state, mail.new, notification
client → server:  typing, read, presence.ping, call.signal
```

Требования: heartbeat каждые 20 с, экспоненциальное переподключение, после реконнекта —
обязательный `GET /sync?since=<last_cursor>`. События батчатся окном 50 мс, чтобы не спамить
клиент при массовых операциях.

## 7. Этапы

Каждый этап заканчивается работающим приложением, которое можно показать. Не переходим к следующему,
пока не выполнены критерии готовности.

### Этап 0 — фундамент (инфраструктура)

Монорепо, `docker-compose` со всеми сервисами, миграции, конфиг через env с валидацией на старте,
структурное логирование, health-эндпоинты, Sentry, GitHub Actions (lint + типы + тесты + сборка),
шаблоны PR и issue, `CONTRIBUTING.md`.

**Параллельно и немедленно (не зависит от кода):** регистрация DNS-записей для почты — A, MX,
SPF, DKIM, DMARC, обратная DNS-запись на IP VPS; запрос в поддержку провайдера на открытие порта 25;
регистрация в Google Postmaster Tools. Репутация домена набирается календарным временем, поэтому
запускается в первый день.

*Готово, когда:* `docker compose up` поднимает всё локально, CI зелёный, `/health` отвечает,
DNS-записи проверены внешним валидатором.

### Этап 1 — ядро мессенджера

Регистрация и вход (логин + пароль, argon2id), сессии устройств, личные и групповые чаты,
история с курсорами, вложения через MinIO, реакции, ответы, правка, удаление, пересылка,
закреплённые, черновики, папки чатов, статусы и присутствие, сквозной поиск, WebSocket-события,
`/sync`. Подключение готового интерфейса из прототипа (`aura-messenger.html` — справочник по
вёрстке и поведению, переносится в React-компоненты).

*Готово, когда:* два клиента переписываются в реальном времени, переживают обрыв связи без потери
сообщений и без дублей, поиск находит по всем разделам, история подгружается страницами.

### Этап 2 — десктопная оболочка

Electron: трей с иконкой и счётчиком непрочитанного, системные уведомления, сворачивание в трей,
глобальные горячие клавиши (включая быстрый ответ и аварийный сброс оформления `Ctrl+Alt+R`),
автозапуск, single-instance. Автообновление через `electron-updater` с провайдером `github` на
публичный `bmf-releases`. Сборки: Windows NSIS + portable, Linux AppImage (с автообновлением)
и `.deb`. Подпись кода — задел на будущее, сейчас документируется как известное ограничение
(SmartScreen будет предупреждать).

*Готово, когда:* установщик ставится на чистой Windows и Linux, приложение находит новую версию
в `bmf-releases`, скачивает и обновляется, трей и уведомления работают при закрытом окне.

### Этап 3 — почта

Stalwart: свои адреса `user@bmf.ink`, привязка к аккаунту, единый ID. Подключение внешних ящиков
по IMAP/SMTP (пароли шифруются, для Gmail — пароль приложения). Папки, чтение, отправка, вложения,
поиск, конструктор правил, отписка, «обсудить в чате», «в задачи» (Pro).

Антиспам-обвязка обязательна с первого дня: лимиты на отправку для новых аккаунтов, счётчики
скорости, **автоматическая заморозка почты аккаунта при подозрении на рассылку** с уведомлением
владельца и ручным разбором, обработка обратной связи от провайдеров. Поддержка нескольких
почтовых доменов на будущее.

*Готово, когда:* письмо с `bmf.ink` доходит до Gmail во «Входящие» (проверка через mail-tester,
оценка ≥ 9/10), внешний ящик подключается и синхронизируется, правила применяются к новым письмам,
заморозка срабатывает на тестовом сценарии массовой отправки.

### Этап 4 — звонки

LiveKit + coturn. Один на один и групповые. **Соединение всегда через сервер по умолчанию**;
P2P — опция в настройках с честным предупреждением, что собеседник увидит IP. Прямое соединение
пробуется 2 секунды, затем молчаливый переход на TURN.

Камера: чтение реального разрешения из `track.getSettings()`, подстройка контейнера под соотношение
сторон камеры (а не наоборот) — это решает обрезание кадра, — плюс переключатель «вписать/заполнить».
Демонстрация экрана со звуком: Windows штатно; Linux — только Wayland через PipeWire-портал, на X11
системный звук недоступен, в интерфейсе показывается явное объяснение вместо тишины.

Панель управления: единая плашка снизу по центру, автоскрытие через 3 секунды бездействия,
возврат по движению мыши; при демонстрации — компактный перетаскиваемый блок. Иконки не
накладываются ни в одной раскладке.

*Готово, когда:* звонок устанавливается между двумя сетями за NAT, групповой на 4 участника
держится 10 минут без деградации, демонстрация экрана со звуком работает на Windows и на Wayland,
кадр камеры не обрезается ни при 4:3, ни при 16:9.

### Этап 5 — остальной функционал

Каналы и подписчики, заметки с markdown и чек-листами, музыкальный плеер (локальная папка
`Music/BMF`), отправка треков в чат, **совместное прослушивание в звонке** (только Pro):
ведущий рассылает позицию и команды, у каждого играет свой локальный файл, синхронизация по
временным меткам с коррекцией дрейфа — аудио в звонок не транслируется. Режим приватности на
libsignal. Маркет: темы, оформления, плагины с экраном разрешений. ИИ-помощник со своим ключом
или Pro. Фундамент подписки: серверная проверка, таблица `subscriptions`, интерфейс уже готов —
приём платежей заглушкой, чтобы позже подключить провайдера без переделки.

*Готово, когда:* все разделы прототипа работают на реальных данных, премиум-функции проверяются
сервером и не включаются патчем клиента.

## 8. Темы и оформление (формат)

Тема — **не код, а конфиг**, интерпретируемый по белому списку ключей. Это свойство формата,
а не результат модерации: внутри нет места, где могло бы жить действие.

Пакет темы: архив с `theme.conf` и папкой `assets/`. Внешние URL запрещены парсером — все
изображения и иконки лежат внутри пакета. При публикации в маркет: пересжатие картинок (убивает
вредное в метаданных), белый список форматов (SVG без скриптов, PNG, WEBP), лимит размера,
проверка контраста, отбрасывание неизвестных ключей.

Приложение открывает **свой собственный конфиг оформления** через настройки: кнопка «Открыть
конфиг» показывает текущие параметры, «Сделать свою тему» копирует их для правки. Пользователь
меняет реальные параметры приложения, а не абстрактную тему — соответствие между форматом и
интерфейсом поддерживать не нужно, это одно и то же.

Плагины — отдельный уровень с разрешениями: манифест описывает, какую кнопку добавить и на какой
адрес отправить данные; список адресов фиксирован в манифесте и принудительно ограничивается;
плагин просыпается только по действию пользователя и получает только тот объект, на котором нажали.
Произвольный JavaScript, доступ к файловой системе и автозапуск не поддерживаются никогда.

**Аварийный сброс `Ctrl+Alt+R`** обрабатывается до применения пользовательского конфига и не может
быть перехвачен темой. Дополнительно: запуск с зажатым Shift стартует без тем.

## 9. Инфраструктура и деплой

### Текущий сервер (бета-тест)

Все сервисы бета-версии живут на **одной машине** — это осознанное решение для теста
на 20 человек, а не архитектурное ограничение. Compose-файлы написаны так, чтобы почта и
звонки выносились на отдельные хосты изменением конфигурации, без правок в коде.

```
host      app.bmf.ink
provider  a VPS in the Netherlands (address omitted in the public copy)
specs     2 vCPU · 8 GB RAM · 60 GB SSD · 100 Mbit/s · unmetered traffic
os        Ubuntu 24.04, no control panel
```

**Учётные данные не хранятся в этом репозитории и ни в одном документе.**
Доступ — только по SSH-ключу; пароли и токены живут в менеджере паролей команды.
Любой секрет, попавший в git, считается скомпрометированным и подлежит немедленной замене:
из истории репозитория его удалить нельзя.

### Обязательная настройка сервера (до первого деплоя)

1. **SSH.** Установить ключ, затем `PermitRootLogin prohibit-password` и
   `PasswordAuthentication no`. Поставить fail2ban. На дешёвых хостингах перебор паролей
   начинается в первые часы после активации.
2. **UFW.** Открыть только 22 (или свой порт), 80, 443, диапазон UDP для LiveKit/coturn
   и, когда дойдёт до почты, 25/465/587/993. Остальное закрыть.
3. **Ротация логов Docker** — обязательна, иначе логи незаметно съедят 60 ГБ:
   `/etc/docker/daemon.json` → `{"log-driver":"json-file","log-opts":{"max-size":"10m","max-file":"3"}}`
4. **Swap.** Проверить `free -h`. На OpenVZ swap часто отсутствует и добавляется только
   провайдером — если его нет, запросить.
5. **PTR-запись** на `app.bmf.ink` в панели хостинга; A-записи `app` и `api` у регистратора.
6. **Проверить IP по чёрным спискам** (MXToolbox Blacklist Check, Spamhaus) сразу после
   активации. Если адрес уже засвечен — требовать замену.
7. **Проверить Docker** до начала работы: `docker run --rm hello-world` и `docker compose version`.
   На OpenVZ Docker работает не у всех провайдеров; на этом — проверено, работает.

### Известные ограничения этого хостинга

- **Порт 25 заблокирован** на тарифах дешевле $19. Пока провайдер не разблокирует его по
  запросу, отправка почты с собственного домена невозможна. Приём почты, IMAP/SMTP чужих
  ящиков и весь интерфейс почты разрабатываются и тестируются независимо от этого.
- **100 Мбит/с** — потолок примерно на 5 одновременных групповых звонков.
- **2 vCPU** — при групповом звонке LiveKit конкурирует за процессор с Postgres и Node.
  Для теста приемлемо; при заметных подтормаживаниях — апгрейд тарифа, не оптимизация кода.
- **OpenVZ**: общее ядро, ресурсы переподписаны, соседи по ноде влияют на дисковый ввод-вывод.

### Хостинг после беты

При выходе из беты меняется хостинг целиком. Чтобы переезд занял вечер, а не неделю:
никаких захардкоженных путей и адресов (всё через env), доступ к файлам только через
S3-клиент, регулярная **проверка восстановления из бэкапа** (переезд — это и есть
восстановление на новой машине), снижение TTL DNS до 300 секунд за сутки до переключения.

Отдельно про почту: репутация отправителя привязана к IP, а не к домену, поэтому переезд
почтового сервера обнуляет прогрев. Постоянный почтовый хост поднимается **один раз** —
на релизном хостинге — и больше не меняется.

### Общие требования

Всё в Docker, оркестрация `docker compose`. Наружу торчит только reverse-proxy (Caddy) с
автоматическим TLS; внутренняя сеть помечена `internal`. LiveKit и coturn работают в
host-режиме — им нужен реальный диапазон UDP-портов.

Бэкапы: ежедневный `pg_dump` + снапшот MinIO, хранение 14 дней, **проверка восстановления
раз в месяц**. Логи: 30 дней. Метрики в Prometheus, дашборды в Grafana, алерты на:
место на диске (порог 75%), недоступность сервисов, очередь почты, ошибки 5xx,
всплеск отправки писем.

Квоты, обязательные на 60 ГБ диска: почтовый ящик 500 МБ на пользователя, срок хранения
медиа с автоочисткой, лимит на размер вложения из `LIMITS`.

## 10. Юридическое и приватность (в коде)

Не юридическая консультация — перед публичным запуском нужен юрист, особенно из-за почты.
Но следующее закладывается в код сразу, потому что потом это дорого:

- полное удаление аккаунта каскадом: сообщения, файлы, почта, ключи, сессии;
- экспорт своих данных одним архивом;
- запись согласия пользователя с версией документа (`consents` с датой и версией);
- срок хранения логов и служебных данных ограничен, не «вечно»;
- минимизация: собираем только логин, почту и пароль;
- на время закрытого теста — честный экран при регистрации: тестовая версия, данные могут быть
  потеряны;
- почтовые адреса на старте выдаются по инвайтам (снижает риск спама и репутационных проблем).

## 11. Качество

Тесты: юнит на бизнес-логику (права, лимиты, правила почты, идемпотентность), интеграционные на
API против реальной базы в контейнере, e2e-сценарий «регистрация → чат → сообщение → звонок».
Покрытие не самоцель, но модули `auth`, `messages`, `mail/rules`, `billing` — обязательно.

Правила: PR только через ветку, CI обязателен, миграции обратимы, никаких секретов в репозитории,
конфиг только из env с валидацией на старте, ошибки — типизированные коды, а не строки.
